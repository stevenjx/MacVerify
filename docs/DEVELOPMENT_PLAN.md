# MacVerify 开发规划

本文件记录 1.0.1 之后的开发方向。所有功能都遵守同一条硬约束：

> **只呈现本机可以实测验证的信息。取不到就显示「不可用」，绝不推断、绝不兜底估算。**

这条约束决定了功能取舍：凡是需要外部数据库（保修状态、Apple 服务端配置、市场价）或需要特权
（SMC、`powermetrics`、内核扩展）的检查项，一律不做，或做成"明确标注不可用"的占位。

---

## 一、本次已完成的修正（1.0.2 前置工作）

这些是代码审查中发现的**确凿错误**，已在本机实测比对系统真值确认并修复。

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | 电池健康度用 `NominalChargeCapacity ÷ DesignCapacity` | 实测 92.0%，系统设置显示 90%，**与用户看到的数字矛盾** | 改用 Apple 官方口径 `AppleRawMaxCapacity ÷ DesignCapacity` → 89.6%，四舍五入 90% |
| 2 | 存储容量取自根卷 `volumeTotalCapacity` | 1TB 机器显示 995 GB，验机时会被误判为容量不足 | 改取物理盘 `diskutil TotalSize`，并按零售规格归一到 1TB |
| 3 | 激活锁靠匹配 `system_profiler` 的英文文本 | 中文系统输出「激活锁状态：已停用」，匹配失败会**静默显示无法读取** | 改用 `-json` 的 `activation_lock_status` 稳定 token |
| 4 | 崩溃日志只找 `*.panic` | macOS 13+ 内核崩溃改为 `*.ips`（bug_type 210），**永远统计为 0** | 同时解析 `.ips` 头部 JSON，并扫描 `Retired/` |
| 5 | 崩溃日志目录不可读时返回 0 条 | 把「读不到」误报成「没有崩溃」，是验机场景里最危险的假阴性 | 新增 `panicScanAvailable`，UI 显示「无法读取」 |
| 6 | `Shell.run` 不读 stderr、进程退出即返回 | stderr 写满会死锁；大段 JSON 被截断成非法数据 | 读到 EOF、丢弃 stderr、超时 terminate 并回收 |
| 7 | **`Process` 释放时崩溃** `task still running` | 命令执行器上线即崩，整个 app 不可用 | 关闭父进程写端 + `waitUntilExit` 兜底 |
| 8 | `EDIDInfo` 未校验校验和、year=0 当成 1990 | 可能把脏数据当面板信息显示 | 加 128 字节校验和验证；year=0 视为未知 |
| 9 | 面板信息只认 EDID | Apple Silicon 不暴露 EDID，面板序列号一直显示不可用 | 改从 `SPDisplaysDataType` 取 vendor/product/serial，**Apple Silicon 上也能读到** |
| 10 | 机型表错误：`MacBookPro16,4` 标成 13 吋 2020 | 2019 款 16 吋会被认成 13 吋 | 对照 Apple 官方列表改正 |
| 11 | 机型表给同标识符硬写芯片（如 `Mac14,9` 标 M2 Pro） | 标识符本身无法区分 Pro/Max，写死即出错 | 名称只保留 Apple 官方写法，芯片一律实时读取 |
| 12 | 未知机型按前缀猜尺寸 | `Mac17,x` 猜成 13 吋，误导验机 | 改为「未收录的机型（Mac17,x）」 |
| 13 | 架构判断用 `#if arch(arm64)` | Rosetta 下 M 系列会显示成 Intel | 按芯片名判断 |
| 14 | 序列号只接受 10/12 位 | 11 位老机型被误标「格式异常」 | 放宽到 10–12 位 + 字母数字校验 |
| 15 | 电池负载测试用 `100 - 循环×0.03` 推断「理论容量」 | 这是编造的衰减模型，据此判「吻合/不吻合」是伪科学 | 删除该模型，只保留 Apple 官方 80%/1000 次口径 |
| 16 | 压降被当成「内阻」 | 10 分钟内电量本身在下降，端电压下降含 SOC 分量，不是纯内阻 | 改称「负载期间电压下降」，文案说明含 SOC 分量 |
| 17 | 全 App 三处健康度阈值不一致（85/80/90） | 同一台机在概览和电池页可能一绿一橙 | 统一为 `HealthGrade`，唯一口径 |
| 18 | 崩溃日志项无法点击跳转 | 概览里的「崩溃记录」点了没反应 | 指向安全页 |

## 二、新增功能：一致性核验（已完成）

**目的**：识别改机型、刷序列号、换屏、换盘。

**方法**：同一事实从两条**互相独立**的通路读取，比对是否一致。不依赖任何外部规格表——
外部表会过期，写错就是新的假数据；而"两个独立来源给出不同答案"本身就是篡改的直接证据。

| 核验项 | 通路 A | 通路 B |
|---|---|---|
| 机型标识 | `system_profiler -json` `machine_model` | `sysctl hw.model` |
| 序列号 | `SPHardwareDataType` `serial_number` | IOKit `IOPlatformExpertDevice` |
| 芯片 | `chip_type` | `sysctl machdep.cpu.brand_string` |
| 磁盘容量 | `diskutil -plist TotalSize` | IOMedia `Size` |
| 硬盘介质 | 介质名是否以 `APPLE SSD` 开头 | — |
| 内建屏 | `SPDisplaysDataType` 面板 product-id | `CGDisplayModelNumber` |
| 内存 | `hw.memsize` 是否落在常见档位 | — |

**已验证**：正常机 7 项全部 `consistent`；构造的篡改机（改机型 + 改序列号 + 换盘 + 换屏）
在 4 项上正确报 `inconsistent`，1 项报 `notice`。

## 三、新增功能：质检报告导出（已完成）

- 导出 Markdown + 同名 JSON
- 每个字段带 `value` / `state` / `note`，取不到的值为 `null` 而非 0
- JSON 结构固定，便于比对两次检测结果或做批量验收
- 支持命令行自检：`MACVERIFY_DUMP_REPORT=/tmp/r.md MacVerify.app/Contents/MacOS/MacVerify`

## 四、后续规划（按优先级）

### P1 — 二手机型真伪核验（已实现 4.1 / 4.2 / 4.3）

实现方式：`Models/ModelSpecCatalog.swift`（Apple 官方规格基线）+ `Services/OriginalityCheck.swift`（比对逻辑）。

| 核验项 | 判据 | 结果状态 |
|---|---|---|
| 内建屏 | 原生分辨率必须与官方一致；对角线偏差 > 0.6″ 记提示 | 不符 → 不匹配 |
| 内存 | `hw.memsize` 必须落在官方可选档位（板载不可更换） | 不在档位 → 不匹配 |
| 存储 | 物理容量与官方档位偏差 ≤ 3% | 超出 → 提示（可换盘） |
| GPU 核心数 | 必须属于官方可选组合 | 不符 → 不匹配 |
| 电池容量 | 设计容量 × 11.45 V 折算 Wh，与官方额定值偏差 ≤ 10% | 超出 → 提示 |
| 电池数据自洽 | 满充容量不得比设计容量高出 5% 以上 | 超出 → 不匹配 |

**基线收录规则**（新增机型必须遵守）：

1. 每条必须能追溯到 Apple 官方技术规格页，`source` 字段写链接；
2. 数值照抄官方页面，不做换算推测；
3. 电池同时记录标注容量与官方脚注的实际额定容量，比对用后者；
4. 未收录的机型显示「无对照数据」，不做任何判断；
5. 新增后在真机上验证屏幕 / 内存 / 存储三项能被正确判定。

当前已收录 4 个机型系列（14″ 2023、16″ 2023、M2 Air 2022、M1 Air 2020），
覆盖 Mac14,5 / Mac14,9 / Mac14,6 / Mac14,10 / Mac14,2 / MacBookAir10,1。

**措辞约束**：不匹配只说明「与官方规格不符」，不能断言「非原装」——
换过整块主板、Apple 官方维修、或基线表本身有误都会产生同样现象。

**待办**：
- 继续补充基线（M1 Pro/Max 14″/16″、M3 / M4 系列、13″ M1/M2 Pro、M2 Air 15″）
- 电池「是否原装」目前只能判容量规格，序列号与 Apple 服务记录无法离线核对

### P1 原始设想（保留备查）

**4.1 电池是否为原装** — 已按「容量规格比对」落地，见上表。
**4.2 内存/存储是否为标称配置** — 已落地。
**4.3 屏幕是否更换** — 已按「分辨率 + 对角线」落地；进一步的面板批次基线需要实机样本，暂不做。

### P2 — 检测项补全（本机可读，但需要新的采集逻辑）

| 功能 | 数据来源 | 可行性 |
|---|---|---|
| Wi-Fi / 蓝牙硬件存在性 | `system_profiler SPAirPortDataType` / `SPBluetoothDataType` | 可做，输出需解析 |
| 摄像头 / 麦克风 / 扬声器存在性 | `SPCameraDataType` / `SPAudioDataType` | 可做，纯枚举 |
| USB / Thunderbolt 设备树 | `SPUSBDataType` / `SPThunderboltDataType` | 可做 |
| 循环次数与使用年限的关系 | 电池循环数 + macOS 安装时间 | 仅提示，不下结论 |
| 固态硬盘通电时长 | 需 SMART，Apple Silicon 不可用 | Intel 机型可做 |

### P3 — 体验与工程

- **检测项开关**：允许用户只跑关心的项，缩短等待
- **两次检测对比**：同一台机不同时间 / 两台机并排对比，标出差异项
- **报告签名**：导出文件带检测时间与机器指纹（序列号哈希），防止报告被换头
- **自动化测试**：把 `ConsistencyAudit`、`EDIDReader.parse`、`healthPercent` 抽成纯函数并加单元测试
  （本次已用 `swiftc` 手工验证，应固化进 CI）
- **构建脚本**：`Scripts/build.sh` 封装 Release 通用二进制 + DMG 打包，避免手工命令出错

### 明确不做

| 需求 | 原因 |
|---|---|
| 电池温度 / 风扇转速 / CPU 温度 | Apple Silicon 无用户态接口，需要特权或私有 API |
| SSD SMART 健康度（Apple Silicon） | 系统不向第三方公开，任何"读到了"的实现都是编的 |
| 激活锁解除状态检测 | 需要 Apple 服务端，涉及账号隐私 |
| 保修剩余 / 是否官翻 | 需要联网查 Apple 服务端 |
| 屏幕坏点自动判定 | 需要摄像头拍摄屏幕，受环境光、摩尔纹影响，无法保证 100% 准确 |
| 二手估价 | 依赖市场数据，不是硬件事实 |

## 五、验收标准

任何新增检测项合入前必须满足：

1. **双源可验证**：能给出至少一条独立通路复核结果
2. **缺失即不可用**：拿不到数据时 UI 显示「不可用」，禁止用 0 / false / 估算值填充
3. **文案不加码**：不确定的结论用「建议确认」，不用「非原装」「故障」
4. **不引入未验证的外部表**：新表必须写明来源，且未覆盖项显示「无对照数据」
5. **实机验证**：至少在一台 Apple Silicon + 一台 Intel（如有）上跑通，并在报告里留证
